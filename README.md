## 무엇을 담고 있나

규정 문서는 일반 텍스트 코퍼스와 다릅니다. **본문과 별표(수치표)가 분리되어 서로를 인용**하고, 자체 규정 위에 상위기관 규정이 있으며, 답변에는 근거 조항이 필수입니다. 표준적인 "청킹 → 임베딩 → 유사도 검색"으로는 반복해서 틀렸습니다.

```
"출장 여비가 얼마인가요?"
  → 제15조(여비)는 찾지만, 정작 금액이 적힌 별표 제3호는 못 찾음
    (표라서 질의와 어휘가 겹치지 않음)
```

이 문제를 임계값 튜닝이 아니라 **문서 구조를 검색 전략에 반영**해서 풀었고, 그 개선이 실제로 효과가 있는지 확인하려고 평가 체계를 만들었습니다. **그 측정이 제 설계 가정을 여러 번 뒤집었습니다.**

## 📊 측정이 뒤집은 설계 가정

| 믿고 있던 가정 | 실측 결과 | 조치 |
|---|---|---|
| 키워드로 검색 대상을 좁히면 정확도가 오른다 | **−9.9%p** — "계약" 같은 흔한 단어가 규정 질의 44건을 공지 컬렉션으로 보냄 | 사전분류 제거 |
| 병목은 별표(표) 검색이다 | 별표 78.4% > **본문 64.9%** — 반대였음 | 그래프 확장 방향 전환 |
| 인용 그래프는 본문→별표 방향 | **별표→본문 역방향이 4배 효과** | 양방향 구현 |
| 원문 직독이 맥락을 보강한다 | 정확도 **7.4%** — 참조 경로 문제로 조문 조각만 반환 중이었음 | 경로 수정 + 인터페이스 교체 |
| 독해 성능이 오르면 실전도 오른다 | 독해 +1.0%p인데 **실전 −14.2%p** | 평가 프로토콜 재설계 |

다섯 가정 모두 "그럴듯한 직관"이었고, **측정 없이는 아무도 몰랐습니다.**

가장 큰 교훈은 인터페이스에서 나왔습니다 — 원문 조회 도구는 참조 경로를 고쳐도 정답이 11건에서 멈췄는데, 남은 실패가 **LLM이 긴 한글 파일명을 옮겨 적는 행위 자체**(전각 문자·확장자 덧붙임·공백 차이)에서 나왔습니다. 방어 로직을 쌓는 대신 **해시 기반 7자 문서 ID**로 인터페이스를 바꾸자, 27건 중 2건이던 정답이 42건 중 21건이 됐습니다. **방어 로직은 한 줄도 늘리지 않았습니다.**

> [!IMPORTANT]
> LLM에게 긴 문자열의 정확한 재생산을 요구하는 인터페이스는 그 자체가 결함입니다.
> 방어 로직은 관측된 변형만 막습니다. 짧은 불변 토큰으로 설계를 바꾸는 편이 근본적이었습니다.

평가셋 설계부터 3차에 걸친 측정, 가정이 뒤집힌 과정까지 전체 기록은 **[EVALUATION.md](docs/EVALUATION.md)** 에 있습니다.

## 🧰 구성

### `eval/` — 평가 체계

측정 없이 개선하지 않기 위해 만든 하니스입니다. **검색과 생성을 분리 측정**하는 것이 핵심 — 답변 정확도만 보면 검색이 문제인지 생성이 문제인지 구분되지 않습니다.

| 파일 | 역할 |
|---|---|
| [`gen_testset.py`](eval/gen_testset.py) | 평가셋 자동 구축. 문서 유형별(본문 / 표 / **본문+표 연계** / 공지) 출제, **표에만 존재하는 값이 정답에 실제로 포함됐는지 기계 검증**해 미달 문항 폐기 |
| [`eval_retrieval.py`](eval/eval_retrieval.py) | Recall@k 측정. 연계형은 본문/표 각각의 회수율로 분해해 **병목 위치를 특정** |
| [`eval_e2e.py`](eval/eval_e2e.py) | 도구 호출 루프를 끝까지 돌린 뒤 LLM-as-a-Judge 채점. 답변·채점 모델 분리 지정, 첫 턴 도구 호출 강제 옵션 |

평가셋 설계에서 중요했던 판단은 **정답 근거 문서를 데이터에 내장**한 것입니다(`source_file`·`linked_file`). 덕분에 "별표는 찾는데 본문을 놓친다" 같은 진단이 가능해졌습니다.

### `sft/` — 에이전트 파인튜닝

큰 모델(35B)의 능력을 작은 모델(8B)로 옮기는 증류 파이프라인입니다. **두 번의 사이클**을 거쳤고, 첫 실패가 더 많은 것을 알려줬습니다.

| 파일 | 역할 |
|---|---|
| [`gen_train_data.py`](sft/gen_train_data.py) | QA 증류. **정답 수치가 원문에 실재하는지 기계 대조**(선생 모델의 환각 차단) + 평가셋 질문 중복 차단(오염 방지) |
| [`gen_agent_traces.py`](sft/gen_agent_traces.py) | **에이전트 궤적 증류** — 질문 → 도구 호출 → 도구 결과 → 답변 전 과정을 녹화. 성공한 궤적만 채택하고 즉답 궤적은 폐기 |
| [`train_lora.py`](sft/train_lora.py) | 단일 턴 LoRA (프롬프트 마스킹) |
| [`train_lora2.py`](sft/train_lora2.py) | **다중 턴 LoRA** — assistant 턴(도구 호출 결정 + 최종 답변)에만 손실. 토큰열에서 블록을 직접 스캔해 템플릿 비대칭으로 인한 마스킹 누수를 차단하고, 학습 전 스팬을 디코드해 육안 검증 |

**1차 실패가 핵심 발견이었습니다.** "컨텍스트 제공 → 즉답" 형식으로만 학습시키자 **검색 도구를 호출하는 습관 자체가 지워졌습니다**(도구 미호출 base 7건 → 학습 후 77건). *"반드시 도구를 먼저 호출하라"* 는 명시적 프롬프트로도 막히지 않았고, API 강제(`tool_choice="required"`)로 원인을 격리한 뒤 **궤적 데이터로 재학습해 394/394 복원**했습니다.

> [!IMPORTANT]
> 행동 제어의 세기: **프롬프트 지시 < API 강제 < 학습 데이터.**
> 에이전트용 SFT 데이터에는 도구 호출 궤적이 반드시 포함되어야 합니다.

### `src/` — 검색 파이프라인 구성요소

| 파일 | 역할 |
|---|---|
| [`citation_graph.py`](src/citation_graph.py) | **인용 관계 그래프 확장**. 본문의 「별표 제N호에 따라…」 인용을 정규식으로 추출해 방향 그래프를 만들고, 검색 결과의 이웃을 **양방향** 확장. 유사도를 재계산하지 않으므로 어휘가 전혀 겹치지 않는 수치표도 회수 |
| [`regulation_agent_tool.py`](src/regulation_agent_tool.py) | 에이전트 도구 구현. 다중 컬렉션 병합, 위계 폴백, **문서 ID 기반 원문 조회**, docstring을 프롬프트 레이어로 활용한 행동 제어 |
| [`filesystem_rag_tool.py`](src/filesystem_rag_tool.py) | 벡터리스 Agentic RAG 실험 — `list → grep → read` 3단으로 LLM이 파일시스템을 직접 탐색 |

## 📈 결과

개선을 한 번에 적용하지 않고 **단계마다 분리 측정**했습니다. 어느 조치가 얼마나 기여했는지 알기 위해서입니다.

**검색 단계** — Recall@5: 정답 근거 문서가 상위 5개에 포함된 비율 (394건)

| | 초기 | 사전분류 제거 | + 그래프 확장 |
|---|---:|---:|---:|
| 전체 | 75.6% | 85.5% | **87.8%** |
| 본문+표 연계 | 60.8% | 71.6% | **81.1%** |

**답변 단계** — End-to-End: 실제 에이전트가 낸 최종 답변을 LLM이 채점 (394건)

| | 검색 개선 후 | 경로 수정 | + 문서 ID |
|---|---:|---:|---:|
| 전체 | 86.0% | 87.8% | **88.6%** |
| 시스템 오류 | 28건 | 16건 | **16건** |

> 두 표는 서로 다른 실험입니다. 답변 단계의 출발점 86.0%는 검색 개선(87.8%)이 이미 적용된 상태이며, 검색 개선이 답변에 미친 영향은 별도로 측정하지 않았습니다. 지표 정의와 차이는 [EVALUATION.md](docs/EVALUATION.md)에 있습니다.

**SLM 파인튜닝** (8B, 실전 E2E)

| 모델 | 정확도 | 도구 사용 |
|---|---:|---:|
| base 8B | 81.5% | 387 / 394 |
| 1차 SFT (즉답 데이터) | 67.3% | 317 / 394 |
| **2차 SFT (궤적 데이터)** | **83.5%** | **394 / 394** |
| 35B (서비스 모델) | 88.6% | 391 / 394 |

8B는 최선의 경우에도 35B와 5.1%p 차이였습니다. **품질 기준으로 교체 근거가 없다고 판단**하고 서비스 모델을 유지하되, 격차가 좁혀질 때의 교환 기준선을 문서화했습니다.

## 실행

각 스크립트는 독립 실행되며, 벡터 DB·LLM 엔드포인트 경로는 환경변수로 지정합니다.

```bash
# 평가셋 구축 (LLM으로 출제 후 기계 검증)
python eval/gen_testset.py --full --out testset.json

# 검색 평가 — 그래프 확장 포함/미포함 비교
python eval/eval_retrieval.py --testset testset.json --topk 5 --graph

# 답변 평가 — 답변 모델과 채점 모델 분리 지정
python eval/eval_e2e.py --testset testset.json \
    --answer-url http://<answer-model>/v1 --judge-url http://<judge-model>/v1

# 에이전트 궤적 증류 후 다중 턴 LoRA 학습
python sft/gen_agent_traces.py --src qa.jsonl --out traces.jsonl
python sft/train_lora2.py --model <base-model> --train traces.jsonl --val val.jsonl --out ./adapter
```

> [!WARNING]
> 이 저장소에는 학습·평가 데이터가 포함되지 않습니다. 대상 문서와 벡터 DB는 별도 구축이 필요합니다.
