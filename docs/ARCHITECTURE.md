# 검색 아키텍처 상세 설계

규정 문서 QA 시스템의 RAG 파이프라인과 에이전트 도구 설계 문서입니다.
개요는 [README](../README.md)를 참조하세요.

---

## 1. 설계 배경

### 대상 문서의 구조적 특성

연구소 규정 문서는 일반 텍스트 코퍼스와 다른 세 가지 성질을 가집니다.

**① 본문과 수치표의 물리적 분리**
조문 본문은 *"여비는 별표 제3호에 따라 지급한다"* 라고만 기술하고, 실제 금액은 **별도 문서(별표)**에 표 형태로 존재합니다. 사용자 질문의 답은 대부분 별표에 있지만, 표는 서술형 질의와 어휘가 겹치지 않아 벡터 검색으로 도달하기 어렵습니다.

**② 조문 간 명시적 상호참조**
`제12조`가 `제5조`를, `제15조`가 `별표 제3호`를 인용하는 구조가 문서 전반에 깔려 있습니다. 즉 **문서 집합 자체가 링크 그래프를 내장**하고 있습니다.

**③ 조직 규정 위계**
연구기관 자체 규정에 없는 사항은 상위기관 규정을 따릅니다. 두 출처를 혼동하면 답변의 신뢰성이 무너집니다.

### 데이터 구축 파이프라인 — 원문에서 검색 가능한 형태까지

검색 이전에, 원문을 검색 가능한 데이터로 만드는 파이프라인을 직접 구축했습니다.

**① 원문 확보** — 규정집 원본은 보안 솔루션(DRM)이 적용된 HWP/HWPX·PDF입니다. 해제 서버와 연동해 파싱 가능한 상태로 만들고, 공지사항은 사내 포털 크롤러로 수집해 정제했습니다.

**② 본문: 조문 단위 구조 분할** — 규정 본문을 고정 길이가 아니라 **조문 단위**(`제N조`·부칙·서문)로 분할하고, `분류_규정명_제N조` 파일명 규칙으로 정규화했습니다. 이 명명 규칙이 이후 상호참조 그래프(계층 4), 문서 ID 인터페이스, 평가셋의 근거 역추적까지 **전 파이프라인의 공통 키**가 됩니다.

**③ 별표: 폐쇄망 VLM 2단 변환** — 별표는 표 중심 문서라 일반 텍스트 추출로는 구조가 깨집니다. 외부 OCR API를 쓸 수 없는 환경이라 **로컬 VLM 2단 파이프라인**으로 변환했습니다: 비전 모델(qwen3-vl:30b)이 페이지 이미지의 표 구조를 읽어내고, 텍스트 모델(qwen3:14b)이 교정·표 정렬을 수행해 **마크다운 표**로 재구성합니다(변환 메타 포함). 이렇게 만든 585개 별표가 검색·그래프·평가셋의 별표 소스입니다.

**④ 색인: 자동 분류와 유형별 차등 청킹** — 파일명·내용 기반으로 문서를 **기능 분류**(서식 Template / 기준표 Criteria / 참고 Reference)와 **부서 카테고리**(인사·연구·회계·총무·안전)로 자동 분류한 뒤, 유형에 따라 청킹을 달리했습니다.

| 유형 | 청킹 전략 | 이유 |
|---|---|---|
| 서식(Template) | 문서 전체 1청크 | 빈칸 양식은 쪼갤 정보가 없음 |
| 기준표(Criteria) | 헤더 단위 대블록 | **표가 중간에 잘리지 않도록** |
| 본문 조문 | 조문 단위 (+장문은 분할) | 구조 경계 = 의미 경계 |

모든 청크에 **문서명 컨텍스트를 접두**해, 청크만 검색돼도 어느 규정의 내용인지 식별되게 했습니다. 임베딩은 qwen3-embedding:8b(로컬 Ollama), 저장은 ChromaDB 컬렉션 분리(규정/별표/공지/상위기관) + 메타데이터 스키마(`doc_name`·`article`·`is_appendix`·분류)입니다.

**⑤ 개정 대응** — 규정은 수시로 개정되므로, 개정분만 재변환·재색인하는 스크립트(`scripts/org/index_updated_regulations.py`)로 운영합니다.

### 표준 RAG의 실패

| # | 실패 | 원인 |
|---|---|---|
| 1 | 답이 담긴 별표 미검색 | 특성 ① — 본문만 검색되고 수치표는 어휘 불일치로 누락 |
| 2 | 단서 조항 소실로 반대 답변 | 청킹이 `"제3항의 경우를 제외한다"` 와 제3항 본문을 분리 |
| 3 | 출처 오인용 | 특성 ③ — 단일 DB에 두 기관 문서 혼재 |
| 4 | 공지사항의 규정 답변 오염 | 성격이 다른 문서가 동일 임베딩 공간에서 경쟁 |

임계값·`top_k` 조정으로는 재현율과 정밀도가 서로를 상쇄할 뿐 해결되지 않았습니다.
**문서 체계의 구조를 검색 전략에 명시적으로 인코딩**하는 방향으로 전환했습니다.

## 2. 세 컬렉션을 한 번에 검색하고 병합한다 (계층 1)

### 폐기된 설계 — 키워드 기반 컬렉션 라우팅

처음에는 질의 성격을 키워드로 판별해 **검색 대상 컬렉션을 미리 좁혔습니다.**

```python
# 2026-08 제거됨
notice_keywords = ["공지", "안내", "식단", "공사", "모집", "계약", "시스템", "변경", ...]
if is_notice_query and not is_reg_query:
    collections = [공지사항]                  # 규정을 아예 보지 않음
elif is_reg_query and not is_notice_query:
    collections = [규정 본문, 별표/서식]
else:
    collections = [규정 본문, 별표/서식, 공지사항]
```

의도는 두 가지였습니다. ①규정 질의에 일회성 공지가 섞여 개정 전 정보로 답하는 것을 막고, ②규정 질의일 때 별표를 **확률이 아니라 고정 규칙으로** 동반 조회한다.

**측정 결과 이 설계는 정확도를 9.9%p 떨어뜨리고 있었습니다.**

| | 라우팅 ON | 라우팅 OFF |
|---|---:|---:|
| 전체 Recall@5 | 75.6% | **85.5%** |

원인은 키워드 목록의 오염이었습니다. `"계약"`·`"교육"`·`"시스템"`·`"공사"` 처럼 **규정에도 흔한 단어가 공지 키워드에 들어 있었고**, 그 결과 규정 질의 44건이 공지 컬렉션만 검색했습니다.

> *"**계약**직원 재임용 심사 기준은?"* → `계약` 매칭 → 공지사항만 검색 → 정답이 있는 규정·별표는 **조회조차 안 됨**

주목할 점은 코드에 남아 있던 주석입니다.

```python
# 공지사항 관련 키워드 대폭 확장 (사용자 요청 반영: 계약, 시스템, 변경 등 포함)
```

"공지가 잘 안 잡힌다"는 요청에 대응해 키워드를 늘린 흔적인데, **측정 수단이 없어 반대편 손실을 아무도 몰랐습니다.** 44건 중 22건이 이때 추가된 `"계약"` 하나에서 발생했습니다.

### 현재 — 전 컬렉션 통합 검색

라우팅을 제거하고 규정·별표·공지를 항상 함께 검색합니다.

원래 우려했던 **공지 오염은 거리(distance) 정렬과 threshold 필터가 이미 걸러주고 있었습니다.** 검색 범위를 미리 배제해 얻는 이득보다, 정답이 든 컬렉션을 통째로 건너뛰는 손실이 훨씬 컸습니다.

> **교훈** — "관련 없는 후보를 미리 쳐내면 정확도가 오른다"는 직관은 **쳐내는 기준이 정확할 때만** 성립합니다.
> 판별기가 부정확하면 배제는 회복 불가능한 손실이 되지만, 점수 기반 정렬은 잘못 섞인 후보를 뒤로 밀 뿐입니다.
> **불확실할 때는 배제보다 순위화가 안전합니다.**

### 결과 병합

컬렉션별로 독립 검색한 뒤 병합합니다. `n_results`를 `top_k × 2`로 과다 조회해 컬렉션 간 결과 수 불균형을 흡수하고, **동일 문서가 여러 경로로 검색되면 더 가까운 거리값을 채택**합니다.

```python
if dist <= threshold:
    if content not in results or dist < results[content]["dist"]:
        results[content] = {"doc": content, "dist": dist, "coll_type": coll_type, ...}

sorted_results = sorted(results.values(), key=lambda x: x["dist"])[:top_k]
```

## 3. 조각으로 찾고 원문으로 승격한다 (계층 2)

> **실측 이력** — 이 계층은 오랫동안 **원문을 읽지 못한 채** 동작하고 있었습니다.
> 참조 디렉토리에 통합 원문이 빠져 있어 조문 조각을 반환하며 턴 소진을 유발했고, 호출한 질의 27건 중 2건만 정답이었습니다.
> 경로를 고치고 파일명 대신 문서 ID로 호출하게 바꾸어 42건 중 21건까지 회복했습니다.
> 추적 과정은 [EVALUATION.md](EVALUATION.md) 참조.

이 시스템의 핵심 구조입니다.

### 문제

청킹은 검색을 가능하게 하는 대신 맥락을 파괴합니다.

- 청크를 **키우면** — 임베딩이 여러 주제를 평균내 검색 정확도 하락
- 청크를 **줄이면** — 단서 조항·예외 규정이 본문과 분리되어 오답 (실패 2)

청크 크기라는 단일 파라미터로는 두 요구를 동시에 만족할 수 없습니다.

### 해결 — 검색 경로 이원화

| 경로 | 도구 | 단위 | 역할 |
|---|---|---|---|
| 1차 · 탐색 | `semantic_search` | 청크 | 넓은 후보에서 **어느 문서를 봐야 하는지** 판별 |
| 2차 · 정독 | `read_regulation_file` | **문서 전체** | 파일시스템에서 원문을 직접 읽어 **완전한 맥락** 확보 |

**두 경로를 잇는 주체는 LLM입니다.**

```
질의 ──▶ [벡터 검색] ──▶ 청크 + 출처 파일명
                              │
                              ▼
                     LLM 판단 (2차 도구 호출 여부 결정)
                     "이 청크로 충분한가?"
                     "단서 조항이 걸려 있는가?"
                              │
                              ▼
                     [파일 직독] ──▶ 규정 전체 원문 ──▶ 답변
```

2차 도구의 docstring이 승격 조건을 규정합니다.

```python
def read_regulation_file(self, filename: str) -> str:
    """
    [심화 검색] 특정 규정 파일의 '전체 내용'을 정독합니다.

    1. 먼저 `semantic_search`를 통해 관련 조항을 찾으세요.
    2. 검색된 조항만으로 답변이 부족하거나, 해당 규정 전체의 맥락 파악이
       꼭 필요할 때만 이 도구를 사용하세요.
    3. 파일명은 `semantic_search` 결과에서 얻은 이름을 정확하게 입력하세요.
    """
```

### 이 구조를 택한 이유

- 벡터 검색은 **"어디를 볼지" 찾는 데는 강하지만 "무엇이 답인지" 확정하는 데는 약합니다.** 전자만 벡터에 맡기고 후자는 원문 전체를 LLM 컨텍스트에 넘겨 판단하게 역할을 분리했습니다.
- 모든 질의에 원문을 넣으면 컨텍스트 낭비와 지연이 발생합니다. **필요할 때만 승격**시키는 조건부 구조라 평균 비용이 낮습니다.
- 검색 실패의 책임을 임계값 튜닝이 아니라 **에이전트의 판단**으로 이전시켜, 검색기 성능 한계를 상위 계층에서 흡수합니다.

## 4. 자체 규정에 없으면 상위기관 규정으로 (계층 3)

```
1차: 연구기관 자체 규정  →  근거 있음      → 답변
                      →  근거 없음/부족 → 2차: 상위기관 상위기관 규정 → 답변
                                        → 둘 다 없음 → "정보 없음" 명시
```

### 도구를 분리한 이유

단일 도구로 두 기관 문서를 함께 검색했을 때, 결과 목록에 출처가 섞이면서 LLM이 연구기관 규정을 상위기관 규정이라 잘못 인용하는 사례가 반복됐습니다. 프롬프트로 "출처를 구분하라"고 지시해도 완전히 막히지 않았습니다.

**도구 자체를 분리하면 호출 이력이 곧 출처 근거**가 됩니다. `semantic_search` 결과에는 상위기관 명칭이 붙을 수 없고, `parent_org_search` 결과에만 붙습니다. 검색 품질 문제를 **프롬프트가 아니라 인터페이스 설계로 해결**한 사례입니다.

각 도구의 docstring에 상호 배타적 출처 규칙을 명시해 이중으로 보강했습니다.

## 5. 인용 관계를 따라 이웃 문서를 끌어온다 (계층 4 · GraphRAG)

> **현재 상태**: 양방향 확장 구현 완료, `semantic_search`에 연결됨.
> 단 Open WebUI 도구는 DB에 등록된 코드를 실행하므로, 실서비스 반영에는 **도구 재등록 + 이미지 재빌드**가 필요합니다.

통합 검색은 별표를 검색 대상에 포함시킬 뿐, **어느 별표가 어느 조문에 딸린 것인지**는 알지 못합니다. 문서 집합에 내장된 참조 구조(특성 ②)를 명시적 그래프로 만들어 이를 보완합니다.

**유사도를 다시 계산하지 않는다**는 점이 핵심입니다. 임베딩 거리와 무관하게, 문서에 이미 적혀 있는 인용 관계를 따라가므로 질의와 어휘가 전혀 겹치지 않는 수치표도 확실히 회수됩니다.

### 그래프 구성

| 요소 | 내용 |
|---|---|
| **노드** | 조문(`제N조`) 및 별표(`별표 제N호`) 단위 문서 |
| **엣지** | 본문에서 정규식으로 추출한 상호참조 (`제12조 → 제5조`, `제15조 → 별표 제3호`) |

```python
# 조문 → 조문
reg_refs = re.findall(r'제\s*(\d+)\s*조', content)
for ref_num in reg_refs:
    target_id = f"{current_reg_name}_제{ref_num}조"
    if target_id in self.documents and target_id != node_id:
        self.graph.add_edge(node_id, target_id)

# 조문 → 별표 (표기 변형 대응)
app_refs = re.findall(r'별표\s*제?\s*(\d+)\s*호?', content)
target_id = target_id_1 if target_id_1 in self.documents else target_id_2 ...
```

### 검색 시 확장

```python
def get_related_documents(self, retrieved_metadatas, limit=3):
    seeds = [self.filename_to_node[name] for meta in retrieved_metadatas ...]

    for seed in seeds:
        for neighbor in self.graph.successors(seed):    # 1-hop 확장
            if neighbor not in seen:
                related_node_ids.append(neighbor)

    related_node_ids.sort(key=lambda n: 0 if "별표" in n else 1)   # 별표 우선
```

### 구현 세부

- **별표 우선 정렬** — 확장된 노드 중 별표를 조문보다 앞에 배치. 사용자가 실제로 원하는 답(금액·배점·기준)이 대부분 별표에 있기 때문
- **파일명 정규화** — 실제 파일명 표기가 일정하지 않아(`별표 제3호` / `별표 3`) 파서가 조문·별표를 구분해 노드 ID를 정규화하고 표기 변형을 모두 시도
- **싱글톤 적재** — 프로세스당 1회만 그래프를 메모리에 구성
- **인코딩 폴백** — UTF-8 실패 시 CP949 재시도 (국내 기관 문서의 인코딩 혼재 대응)

## 6. 에이전트 도구 설계

### 도구 정의를 프롬프트 레이어로 활용

Open WebUI의 도구는 **docstring이 그대로 LLM에게 전달되는 함수 스펙**이 됩니다. 이 특성을 활용해 시스템 프롬프트를 비대하게 만들지 않고 도구 단위로 행동을 제어했습니다.

각 docstring에 네 가지를 함께 기술합니다.

| 항목 | 예시 |
|---|---|
| **환각 억제** | *"내부 지식을 사용하지 말 것. 규정은 수시로 개정되므로 검색 결과만을 근거로 할 것"* |
| **도구 연쇄** | *"결과가 부족하면 즉시 `parent_org_search`를 호출할 것"* |
| **출처 규칙** | *"이 도구의 결과에 상위기관 명칭을 붙이지 말 것"* |
| **출력 규격** | *"수치 데이터는 마크다운 표로, 하단에 근거 조항 명시"* |

도구 정의만으로 다단계 워크플로가 성립하므로, **도구를 추가·교체해도 상위 프롬프트를 수정할 필요가 없습니다.**

### LLM 출력 비결정성에 대한 방어

계층 2는 **LLM이 1차 결과의 파일명을 2차 도구에 정확히 전달**해야 성립합니다. 운영 중 다음 변형이 관측됐습니다.

| 관측된 오류 | 원인 | 대응 |
|---|---|---|
| 전각 문자 혼입 (`＿`) | 출력 시 `_`가 마크다운 이탤릭으로 해석되는 것을 막으려 전각 변환했는데, LLM이 그대로 되돌려줌 | 입력단에서 전각 → 반각 역변환 |
| 임의 번호 삽입 (`_07_`) | 문서 목록의 번호 패턴을 학습해 없는 번호를 생성 | 정규식으로 번호 패턴 제거 후 매칭 |
| 확장자·공백 불일치 | 표기 흔들림 | 확장자 제거 + 공백 정규화 후 비교 |
| 부정확한 문서명 | 유사 명칭으로 생성 | 1차 정확 매칭 → **2차 부분 매칭 폴백** |

```python
filename = filename.replace("＿", "_")                    # 전각 → 반각
clean_input = re.sub(r'\s+', ' ', filename.replace(".txt", "").strip())
clean_input_normalized = re.sub(r'_\d+_', '_', clean_input)    # 임의 번호 제거
```

> **원칙** — 에이전트 도구는 프로그램이 아니라 **확률적 생성기가 호출하는 인터페이스**입니다.
> 입력이 스펙대로 들어온다고 가정하면 파이프라인이 끊깁니다. 도구 경계마다 정규화·폴백을 둡니다.

### 멀티쿼리 확장 (PDF 에이전트)

사용자의 구어체 질문은 문서의 공식 용어와 어휘가 달라 검색이 실패합니다. LLM으로 질의를 키워드 중심으로 재작성해 원문 질의와 함께 검색합니다.

```python
tasks = [expand_query_task(session) for _ in range(2)]
expanded_results = await asyncio.gather(*tasks)     # 원문 + 확장 쿼리 병렬 임베딩
```

추론 모델이 출력하는 `<think>` 블록을 정규식으로 제거하는 후처리를 포함합니다.

> **트레이드오프** — 이 확장은 규정 검색 도구(`regulation_agent_tool`)에서 **의도적으로 비활성화**했습니다.
> 확장 쿼리 생성에 LLM 왕복이 추가되어 지연이 커지는 데 비해, 규정 질의는 이미 공식 용어를 포함하는 경우가 많아 정확도 이득이 크지 않았습니다. 코드는 주석으로 보존해 재활성화 가능한 상태입니다.

## 8. 대안 경로 — 벡터리스 Agentic RAG

`filesystem_rag_tool.py` 는 임베딩·벡터 DB 없이 **LLM이 파일시스템을 직접 탐색**하는 실험적 검색 경로입니다.
유닉스 커맨드라인의 탐색 방식(`ls` → `grep` → `cat`)을 도구 3종으로 옮겼습니다.

| 단계 | 도구 | 역할 |
|---|---|---|
| 1 | `list_files(category, keyword)` | 파일명 필터링으로 후보 좁히기 |
| 2 | `grep_content(pattern, context_lines)` | 본문 정규식 검색 + 주변 컨텍스트 반환 |
| 3 | `read_file(filename, category)` | 확정된 문서 전문 읽기 |

### 설계 의도

계층 2의 하이브리드 검색이 **벡터 검색을 거쳐 원문에 도달**한다면, 이 경로는 **처음부터 원문만 다룹니다.**
LLM이 탐색 전략 자체를 수립하게 맡기는 구조로, 벡터 검색을 파이프라인 고정 요소가 아니라 **선택 가능한 도구**로 격하시킨 실험입니다.

```python
CATEGORY_DIRS = {
    "규정": os.path.join(CORPUS_ROOT, "regulation_txt_merged"),
    "별표": os.path.join(CORPUS_ROOT, "regulation_md_merged"),
    "공지": os.path.join(CORPUS_ROOT, "crawled_data", "analyzed"),
}
MAX_FILE_BYTES = 200_000   # 단일 파일 응답 상한 (LLM 컨텍스트 보호)
```

각 도구의 docstring에 사용 조건을 명시해 탐색 효율을 유도합니다.
예를 들어 `list_files`는 *"파일 수가 많으므로 keyword 없이 호출하지 마세요. 2~3글자 핵심어를 함께 넘기세요"* 라고 지시해, LLM이 전체 목록을 요청해 컨텍스트를 낭비하는 것을 막습니다.

### 트레이드오프

| 장점 | 한계 |
|---|---|
| 인덱싱 파이프라인 불필요 — 문서 추가 시 **즉시 반영** | 질의당 LLM 왕복 3회 이상 → 지연 증가 |
| 정규식 기반이라 **정확한 표현 매칭**에 강함 | 동의어·의역 질의에 취약 (벡터 검색의 강점) |
| 임베딩 비용·벡터 DB 운영 부담 없음 | 문서 수 증가 시 grep 비용 선형 증가 |
| 경로를 `CORPUS_ROOT` 환경변수로 통일해 이식성 확보 | 폴더 구조 변경에 민감 |

두 경로는 상호 배타가 아니라 **보완 관계**입니다. 정확한 용어가 포함된 질의는 벡터 검색 없이도 grep으로 충분하고, 의역·구어체 질의는 벡터 검색이 유리합니다. 질의 성격에 따라 경로를 선택하는 구성을 검토 중입니다.

## 9. 검색 품질 평가

설계가 실제로 맞는지 재기 위해 **394건 평가셋을 구축하고 검색·답변을 분리 측정**했습니다. 여기서 위 설계 가정 여러 개가 반증됐습니다.

| 단계 | 지표 | 결과 |
|---|---|---|
| 검색 상한 | Recall@5, 평가 스크립트 (394건) | 75.6% → **87.8%** |
| **검색 실측** | 운영 도구가 모델에게 건네는 5개 기준 (394건) | **82.2%** |
| 답변 | LLM-as-a-Judge (394건) | 86.0% → **88.6%** |

- 키워드 라우팅(2절)은 정확도를 **9.9%p 떨어뜨리고** 있었습니다 → 제거
- 병목은 별표가 아니라 **본문 검색**이었습니다 (64.9% vs 78.4%)
- 그래프 확장(5절)은 **역방향이 4배 효과적**이었습니다
- 원문 승격 도구(3절)는 참조 경로 누락으로 **거의 동작하지 않고 있었습니다**
- 2절의 병합·절단(세 컬렉션 통틀어 상위 5개)이 **연계 유형 정답의 절반을 밀어내고** 있었고, 그래프 확장(5절)이 그 절반을 되찾아오고 있었습니다 (44.6% → 68.9%). 평가 스크립트는 절단 없이 합집합을 봐서 이 효과를 작게 읽었습니다.

평가셋 설계, 3차에 걸친 측정, 뒤집힌 가정, 원문 직독 도구 추적, 그리고 평가 스크립트 자체의 검증 — 전체 기록은 **[EVALUATION.md](EVALUATION.md)** 에 있습니다.
