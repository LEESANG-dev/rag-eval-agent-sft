# 서빙 아키텍처 — 폐쇄망 온프레미스 배포

문서 검색 에이전트를 사내 서비스로 올리면서 내린 결정과 그 근거를 정리했습니다. 검색 품질은 [ARCHITECTURE.md](ARCHITECTURE.md)에, 모델 튜닝은 [FINETUNING.md](FINETUNING.md)에 있습니다.

전제는 두 가지였습니다. **외부망이 차단된 환경**이고, **앱 서버에 GPU가 없다**는 것입니다.

---

## 1. 전체 구성

```
브라우저
   │  HTTPS
   ▼
┌─ 앱 서버 (Ubuntu, on-prem, GPU 없음) ────────────────────┐
│                                                          │
│  nginx          TLS 종료 · WebSocket 업그레이드 중계      │
│    │  proxy_pass → 127.0.0.1:8080                        │
│    ▼                                                     │
│  webui 컨테이너   uvicorn 워커 8 (프로세스)                │
│    │                                                     │
│    ├── redis 컨테이너   워커 간 Socket.IO pub/sub          │
│    │                                                     │
│    └── SSH 터널 (systemd)                                 │
│          127.0.0.1:8000   → vLLM (qwen3.6-35B-A3B)       │
│          127.0.0.1:21434  → Ollama                       │
│          127.0.0.1:21435  → Ollama 임베딩                 │
└──────────────────────────────────┼───────────────────────┘
                                   ▼  외부 GPU 서버
```

앱 컨테이너는 `127.0.0.1:8080`에만 바인딩합니다. **nginx를 거치지 않으면 도달할 수 없습니다.**

## 2. 결정 네 가지와 근거

### ① 워커를 8개 — 스레드가 아니라 프로세스

Python은 GIL 때문에 한 프로세스 안에서 스레드를 늘려도 CPU 연산이 병렬화되지 않습니다. 동시 요청을 받으려면 **인터프리터 자체를 여러 개** 띄우는 수밖에 없습니다.

```bash
uvicorn open_webui.main:app --workers ${UVICORN_WORKERS}
```

수를 8로 정한 것은 **앱 서버 RAM이 7.8GB**였기 때문입니다. 프로세스마다 인터프리터와 앱이 통째로 메모리에 올라가므로, 병목은 GPU가 아니라 앱 서버 메모리였습니다. 부하를 보며 6~12 범위에서 조정 가능하도록 환경변수로 뺐습니다.

프로세스로 나눈 대가는 **메모리 격리**입니다. 이 격리가 아래 두 결정을 강제했습니다.

### ② Redis — 소켓이 워커 메모리에 살기 때문

LLM 응답은 토큰이 하나씩 생성됩니다. 완성될 때까지 기다렸다 한 번에 주면 사용자는 빈 화면을 오래 봅니다. 그래서 생성되는 대로 밀어주는 **WebSocket 스트리밍**이 필요하고, 그 연결 객체는 **연결을 수락한 워커의 메모리에만** 존재합니다.

문제는 연결과 요청의 수명이 다르다는 점입니다.

```
WebSocket 연결   한 번 맺으면 그 워커에 고정        (워커 7)
HTTP 요청        매번 임의의 워커가 처리            (이번엔 워커 3)
```

워커 3이 토큰을 만들어도 워커 7의 소켓에는 손댈 수 없습니다. 그래서 pub/sub 중계를 붙였습니다.

```
WEBSOCKET_MANAGER=redis
REDIS_URL=redis://localhost:6379
```

```
워커 3  토큰 생성 ──publish──▶ Redis ──▶ 워커 7  소켓 보유 ──▶ 브라우저
```

**Redis가 공유하는 것은 이벤트 전달 경로이지 대화 내용이 아닙니다.** 대화 이력은 SQLite에 있고 볼륨으로 모든 워커가 같은 파일을 봅니다. LLM은 상태를 갖지 않으므로 매 요청마다 이력 전체를 다시 전송합니다 — 워커가 바뀌어도 맥락은 유지됩니다.

### ③ nginx — 관문이자 프로토콜 중계

앱은 HTTP만 처리합니다. TLS와 외부 노출은 전부 nginx가 맡습니다.

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;

    proxy_http_version 1.1;
    proxy_set_header Upgrade    $http_upgrade;      # WebSocket 승격 전달
    proxy_set_header Connection "upgrade";

    proxy_buffering    off;                          # 스트리밍 유지
    proxy_read_timeout 86400s;                       # 장시간 응답 허용
    client_max_body_size 100M;
}
```

네 가지가 각각 다른 문제를 막습니다.

- **`Upgrade`/`Connection`** — WebSocket은 일반 HTTP 요청으로 시작해 업그레이드로 승격됩니다. 이 헤더를 전달하지 않으면 승격이 실패하고 **소켓 자체가 생기지 않습니다.** ②의 전제가 무너집니다.
- **`proxy_buffering off`** — 기본값이면 nginx가 토큰을 모았다 한 번에 내보내 스트리밍이 무의미해집니다.
- **`proxy_read_timeout`** — 기본 60초로는 긴 추론 도중 연결이 끊깁니다.
- **`client_max_body_size`** — 문서 업로드를 허용합니다.

인증서는 기관 와일드카드를 재사용했습니다. 서브도메인만 할당받으면 인증서 발급 절차 없이 HTTPS가 성립합니다. 갱신·도메인 변경이 전부 nginx 계층에서 끝나 **앱을 건드리지 않습니다.**

### ④ SSH 터널 — 방화벽 우회가 아니라 경로 고정

앱 서버와 GPU 서버가 분리돼 있고, 방화벽 정책상 추론 포트를 직결할 수 없었습니다. autossh로 터널을 열고 **systemd 서비스로 등록**해 재부팅 후에도 자립하게 했습니다.

터널 덕에 앱 코드는 추론 서버가 원격이라는 사실을 모릅니다. 전부 `127.0.0.1`로 호출합니다. 이 성질은 파인튜닝 평가에서도 쓰였습니다 — 8B 모델을 터널 반대편에 붙이는 것만으로 **운영 파이프라인을 그대로 둔 채** 모델만 교체해 측정할 수 있었습니다([FINETUNING.md](FINETUNING.md)).

## 3. 실패 모드

각 설정이 빠졌을 때 나타나는 증상입니다. 증상이 원인에서 한 단계 떨어져 있어 오진하기 쉬운 항목을 표시했습니다.

| 빠진 것 | 증상 | 오진하기 쉬움 |
|---|---|---|
| `Upgrade` 헤더 | 실시간 갱신이 전혀 안 됨, 새로고침해야 보임 | |
| Redis pub/sub | 워커 수만큼 확률적으로 응답이 화면에 안 나타남 | ⚠️ 그 턴이 저장되지 않아 **다음 질문에서 맥락이 끊긴 것처럼 보임** |
| `proxy_buffering off` | 답변이 한꺼번에 뭉쳐서 나옴 | ⚠️ 모델이 느린 것으로 오해 |
| `proxy_read_timeout` | 긴 답변이 중간에 잘림 | ⚠️ 모델 출력 길이 제한으로 오해 |
| 워커 1개 | 동시 사용 시 순차 대기 | |
| 이전 턴 도구 결과 제거 | 대화가 길어질수록 첫 토큰까지 느려짐 | ⚠️ 모델이나 검색이 느려진 것으로 오해 |

**Redis 항목이 특히 그렇습니다.** 근본 원인은 전달 실패인데, 사용자에게는 "대화 맥락이 끊긴다"로 관측됩니다. 원인과 증상이 다른 계층에 있습니다.

### 이력이 무거워지는 이유

실제 20턴 대화 하나를 꺼내 다음 턴에 실릴 형태로 토큰을 재니 **38,384토큰**이었습니다. 도구를 쓴 턴의 assistant 메시지가 평균 1,900토큰, 최대 8,160토큰입니다.

원인은 프론트엔드가 이전 메시지를 조립하는 방식입니다. 추론 블록(`reasoning`)은 벗겨서 보내는데, **도구 호출 블록은 그 결과값(검색 결과 5개, 원문 전문)을 본문에 남긴 채** 보냅니다. 3턴 전에 본 검색 결과가 매 턴 다시 올라갑니다. 새 질문에 답하는 데 지난 턴의 검색 덤프는 거의 필요 없으니, `reasoning`과 같은 방식으로 벗기면 이력이 대략 5분의 1로 줄 것으로 봅니다. 다만 "아까 그 별표 다시 보여줘" 같은 후속 질문은 약해지므로 트레이드오프입니다.

상한 자체는 여유가 있습니다. 서빙 `max_model_len`은 131,072이고, 모델이 하이브리드 어텐션(40층 중 full-attention 10층, KV 헤드 2개)이라 KV 캐시가 **토큰당 약 20KB**입니다. 최대 길이 시퀀스 하나가 2.6GB이고, 동시 64명 × 30K 토큰도 40GB 남짓입니다. 부하 테스트(100명 × 16K, 에러 0%)와 부합합니다. **먼저 무너지는 것은 메모리가 아니라 첫 토큰까지의 지연입니다.** 검색 결과를 15개로 늘리는 실험([EVALUATION.md](EVALUATION.md) 7장)에서 프롬프트 토큰이 42% 늘 때 지연도 36% 늘었습니다.

## 4. 인프라 제약이 애플리케이션 설계에 미친 영향

워커 간 메모리 격리는 배포만의 문제가 아니라 **도구 인터페이스 설계까지 결정**했습니다.

에이전트가 문서 전문을 열 때 쓰는 식별자를 파일명 대신 짧은 고정 토큰으로 바꾸면서([ARCHITECTURE.md](ARCHITECTURE.md) 참조), 그 값을 **저장하지 않고 계산으로 유도**하도록 설계했습니다.

```python
doc_id = "D" + md5(normalize(filename))[:6]
```

검색은 3번 워커가, 원문 조회는 7번 워커가 처리할 수 있습니다. 두 워커는 메모리를 공유하지 않으므로, 식별자를 테이블에 담았다면 워커 간 동기화 계층이 하나 더 필요했을 것입니다. **결정적 함수로 유도하니 상태 공유 자체가 사라졌습니다.**

멀티 워커라는 제약을 알고 설계했기에 나온 형태입니다.

## 6. 운영상 선택

- **데이터를 이미지에서 분리** — 문서 원문과 벡터DB는 볼륨 마운트입니다. 문서가 갱신돼도 이미지를 다시 빌드하지 않습니다.
- **경로를 환경변수로 추상화** — `CORPUS_ROOT` 하나로 개발(Windows)과 운영(Linux)을 코드 수정 없이 오갑니다.
- **세션 무중단 이전** — 서버를 옮길 때 `WEBUI_SECRET_KEY`를 함께 이전해 사용자 재로그인 없이 마이그레이션했습니다.
- **이미지 경량화** — 임베딩과 추론이 모두 외부 GPU 서버에 있으므로, 빌드 시 CUDA·번들 모델을 제외했습니다.

## 7. 남은 과제

- **단일 앱 서버** — 앱 서버 자체는 이중화돼 있지 않습니다. 현재 사용량 기준으로는 과설계라 판단했으나, 가용성 요구가 올라가면 다중화와 세션 스토어 외부화가 선행되어야 합니다.
- **관측성** — 부하 테스트는 별도 수행했지만 상시 메트릭 수집(워커별 지연, 큐 대기, 터널 상태)은 갖추지 않았습니다. 장애를 사후에 재구성하기 어렵습니다.
- **터널 단일 장애점** — systemd로 자동 복구되지만, 터널이 끊긴 동안의 요청은 실패합니다. 재시도·회로차단기 계층이 없습니다.
- **이력 재전송** — 이전 턴의 도구 결과가 매 턴 다시 올라갑니다(3장). 벗길지, 요약해 남길지, 마지막 N턴만 남길지 아직 정하지 않았습니다. 후속 질문 품질과 지연의 교환이라 E2E로 재고 정할 문제입니다.
